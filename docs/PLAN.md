# Firebird — план согласованного MVP

Команда: Естай (`Adventkz`) и Бекзат (`AbaevnaBeka`). Кейс №6, «Умный подбор подрядчиков». Документ подготовлен 23.09.2026. Это проектные решения, а не утверждение о готовности приложения.

## Границы

Параметры мероприятия → проверка условий → стабильный подбор до трёх подрядчиков → индивидуальные объяснения. Источник — исходные 66 профилей организатора. Бронирование, оплата, регистрация, переписка с подрядчиками, обучение модели и расширение каталога не входят в MVP.

## Архитектура

- Интерфейс: форма, карточки, объяснение пустой/короткой выдачи, три демонстрационных запроса; обращается только к API приложения.
- Сервер: загрузка и проверка CSV при запуске → фильтрация → детерминированное ранжирование → объяснения по проверяемым фактам.
- AI-слой: помогает выбрать релевантные фрагменты описания для объяснений. Не меняет кандидатов, цены, условия или порядок. Реализация должна честно отражать фактически используемую AI-функцию.
- Хранение: исходный CSV в репозитории, нормализованный каталог в памяти. База данных, векторный поиск и RAG по PDF не нужны для этого MVP.
- За основу можно взять опубликованный agent-kit с сохранением MIT-лицензии и раскрытием происхождения. Не переносить старые публичные chat/upload/delete endpoints, не относящиеся к кейсу.
- Один публичный сервис. API-ключ только на сервере; не в браузере, Git, тестовых фикстурах или сообщениях. У Бекзат отдельный явно помеченный UI-деморежим без ключа.

## Точные правила — продуктовые решения команды

1. Валидировать запрос до поиска: известные значения справочников, положительный бюджет, положительная длительность при наличии, дата в диапазоне 2026-09-23…2026-12-31 включительно. Невалидный ввод — 422, не «ничего не найдено».
2. Сначала отобрать город + категорию. Нет записей — `category_missing`.
3. Затем последовательно применить: свободен по календарю → берёт формат → начальная цена не выше бюджета → язык (если задан) → длительность (если задана).
4. Язык и длительность считаем обязательными условиями, когда пользователь их указал. Пустые значения означают «без ограничения».
5. `max_hours=null` означает неприменимость ограничения; такого кандидата не исключать по длительности. Равенство цены бюджету и длительности лимиту допустимо. Бюджет — на одного подрядчика за мероприятие, не на весь комплект услуг.
6. Категории, форматы, языки и занятые даты в CSV разделены `|`. Булевы строки `True`/`False` разобрать явно. Проверить 66 уникальных ID и корректность чисел/дат при запуске; не изменять оригинальный файл.
7. Структурированные поля определяют фильтрацию. Описание — источник особенностей, не способ обойти фильтры. При явном конфликте с описанием не использовать спорный фрагмент как доказательство.
8. Порядок: наличие прямого упоминания нужного формата в описании (1 перед 0), затем цена по возрастанию, затем ID по возрастанию. Это объяснимое правило приоритета, не рейтинг качества подрядчика. В первой версии не делать скрытых весов или случайного ранжирования.
9. Признак упоминания: нормализовать регистр и `ё→е`; искать начало слова `свад` / `корпоратив` / `конференц` / `юбиле` для соответствующих форматов; для дня рождения фразы `день рождения` или `дня рождения`; для тоя отдельное слово `той`. Признак не влияет на допуск кандидата. Правило простое, ограничение описать в README.
10. Вернуть первые три из отсортированных подходящих. Те же параметры и та же версия каталога всегда дают тот же порядок независимо от AI.
11. Причины исключения считать по последовательному первому отказу, чтобы суммы не дублировались. В UI объяснять, что это последовательные фильтры. Нельзя суммировать пересекающиеся причины как число людей.
12. Если подходящих нет, вернуть `no_matches`, причины и совет изменить конкретное ограничение. Не менять условия пользователя автоматически. Если подходящих один или два, показать только их и причину сокращения. Площадки проходят те же проверки, что люди.

## Доказательные объяснения

Карточка: 1–2 предложения с параметрами запроса и индивидуальной особенностью из описания. Цена всегда «от … ₸», дата — «не отмечен занятым в предоставленном календаре», не подтверждённая бронь.

Безопасный минимальный AI-вариант: сервер нарезает описание на пронумерованные фрагменты; модель выбирает релевантный фрагмент по ID для каждого из уже выбранных подрядчиков. Сервер проверяет ID и формирует объяснение из исходного фрагмента и структурированных фактов. Текст источника считать данными, а не инструкциями. Не добавлять неподтверждённые рейтинги, опыт, отзывы или гарантии.

Один AI-запрос на выдачу, ограниченный таймаут и размер ответа. При отсутствии ключа, ошибке или неверном ответе — локальное объяснение по тем же фактам с отметкой `local`. Реальный API должен быть отдельно проверен до сдачи; локальный режим не выдавать за работающую модель. Целевой ответ — до 10 секунд, сетевой таймаут оставить с запасом для остальной обработки.

## Разделение без конфликтов

| Ответственный | Владеет файлами | Не редактирует |
|---|---|---|
| Естай + его Codex | `backend/**`, `data/**`, корневые файлы запуска/лицензия/README, CI, Dockerfile, `.env.example`, `docs/API_CONTRACT.md`, этот план | `frontend/**`, `docs/UI_QA.md` до интеграции |
| Бекзат + её Codex | `frontend/**`, `docs/UI_QA.md` | backend, данные, контракт, корневые файлы, деплой |

Ветки: `feat/matching-api` и `feat/contractor-ui`. Каждый участник работает в своей локальной копии и коммитит под собственной личностью. Не подставлять чужое авторство. Естай интегрирует ветки. Контракт меняется только после сообщения обоим участникам. Никаких force-push и переписывания чужой истории.

Сейчас клонирован командный репозиторий; файлов приложения в нём ещё нет. Перед началом параллельной реализации капитан должен опубликовать согласованные документы, чтобы обе ветки стартовали от одного коммита. Этот документ сам по себе не означает, что push уже выполнен.

## Контрольные точки, если официальный старт был в 13:00

- До 14:00: документы/контракт/данные или другой осмысленный первый результат в командной истории Git. Не пустой коммит.
- До 15:00: сквозной подбор с реальными данными; интерфейс соединён с API хотя бы локально.
- До 16:00: AI-слой, локальный fallback, пустые результаты, тесты, публичная проверка.
- В 16:30 заморозка функций. До 17:00 стабилизация и документация, финальный час — проверки и сдача.
- До подтверждённого дедлайна: публичная ссылка инкогнито/телефон, README, команды запуска, две репетиции. Если старт/дедлайн другие, сдвинуть расписание по официальному объявлению. Автоматические напоминания пока не настроены.

## Приёмка и реальные демонстрационные запросы

Эти количества рассчитаны по CSV, это не результаты тестирования приложения.

- Алматы / Ведущий / корпоратив / 2026-10-10 / 1 000 000 ₸ / русский / 4 ч: до ранжирования подходят HK-88430, HK-77838, HK-27222, HK-29829.
- Тот же запрос на 2026-10-11: HK-44733, HK-44923, HK-77838, HK-27222. Показать влияние календаря, а не утверждать, что любая смена даты обязательно меняет выдачу.
- Алматы / Флорист / свадьба / 2026-10-10 / 300 000 ₸ / без языка и длительности: только HK-39372.
- Алматы / Ведущий / корпоратив / 2026-10-10 / 1 000 ₸: кандидаты есть, бюджет не проходит.
- Зарубежье / Флорист / свадьба / 2026-10-10 / 300 000 ₸: категории в этой локации нет.
- Дополнительные тесты: занятые площадки, точные границы цены и часов, null-лимит, вне календаря, одинаковый запрос дважды, недоступный AI, некорректные параметры, более трёх подходящих.

README: проблема/ценность, ограничения данных, правила подбора, роль AI, фактические тесты, запуск с ключом и без, ссылка демо, источники и лицензии, вклад участников. Проверяющим не требуются личные аккаунты команды. Раскрыть каркас и исходный каталог, не утверждать соответствие ещё не проверенным пунктам общего регламента.
